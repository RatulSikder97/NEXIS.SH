# Phase 3.5 — Workspaces + Billing — Design

**Date:** 2026-05-13
**Phase:** 3.5 (between Phase 3 console and Phase 4 pipeline substrate).
**Dependencies:** Phase 3 (completed 2026-05-13).
**External services:** all local mocks; real Stripe lands in Phase 7.

---

## 1. Goals

1. **Workspace concept** — owner creates one or more workspaces inside their org. Workspace = name + region + status (`provisioning|ready|error|suspended`). All future compute resources (Phase 4 pipelines, Phase 5 agents) attach to a workspace.
2. **Onboarding flow** — after signup, owner is redirected to `/onboarding/workspace`. The console is unreachable until a workspace exists.
3. **Provisioning animation** — SSE-driven state machine streams 5 phases (creating org → allocating host → provisioning datacenter → deploying → ready) over ~6 seconds. Persisted on the server so a refresh shows the current status.
4. **Workspace UI** — sidebar workspace switcher (collapsed-friendly), topbar badge with region, settings page listing workspaces with the region pill and status dot.
5. **Billing (Stripe-style, mocked)** — Settings → Billing surface with: payment method form (card number / exp / CVC / postal), invoices table (monthly billing periods), and current-period usage breakdown by workspace by project.
6. **AWS-style metering** — control-plane cron records `usage_records` every minute for workspaces in `status=ready`, at a fixed rate of $0.10 / runtime hour for Phase 3.5. Phase 4+ adds compute/memory/storage line items.

## 2. Non-goals

- Real Stripe API calls (Phase 7 swaps the adapter).
- Real datacenter provisioning — the animation is theater; the row is just an `INSERT`.
- Per-workspace RLS (Phase 4 introduces workspace-scoped tenant tables; Phase 3.5 stays org-scoped).
- Plan tiers / pricing pages (Phase 7).
- Invoice PDF generation (Phase 7).
- Email receipts (Phase 7).

## 4. Database

### 4.1 New tables

```
workspaces
  id              uuid PK
  org_id          uuid REFERENCES organizations(id)
  name            text NOT NULL
  slug            text NOT NULL
  region          text NOT NULL                 -- e.g. 'us-east-1'
  status          text NOT NULL                 -- 'provisioning'|'ready'|'error'|'suspended'
  status_message  text
  provisioning_step text                        -- last completed step name; nullable
  created_at      timestamptz NOT NULL DEFAULT now()
  ready_at        timestamptz
  updated_at      timestamptz NOT NULL DEFAULT now()
  UNIQUE (org_id, slug)

payment_methods
  id                       uuid PK
  org_id                   uuid REFERENCES organizations(id) UNIQUE  -- one PM per org for Phase 3.5
  provider                 text NOT NULL                              -- 'local' | 'stripe'
  external_customer_id     text
  external_payment_method_id text
  brand                    text                                      -- 'visa'|'mc'|...
  last4                    text
  exp_month                int
  exp_year                 int
  billing_email            text
  created_at               timestamptz NOT NULL DEFAULT now()

invoices
  id            uuid PK
  org_id        uuid REFERENCES organizations(id)
  period_start  timestamptz NOT NULL
  period_end    timestamptz NOT NULL
  total_cents   bigint NOT NULL DEFAULT 0
  status        text NOT NULL                  -- 'open'|'paid'|'void'
  created_at    timestamptz NOT NULL DEFAULT now()
  UNIQUE (org_id, period_start)

usage_records
  id            uuid PK
  org_id        uuid REFERENCES organizations(id)
  workspace_id  uuid REFERENCES workspaces(id)
  project       text NOT NULL DEFAULT 'default'   -- Phase 4+ uses real project names
  kind          text NOT NULL                     -- 'runtime_hours'
  quantity      numeric(20, 6) NOT NULL           -- e.g. 0.016667 = 1 minute
  unit_price_cents numeric(20, 6) NOT NULL        -- e.g. 10.0 (= $0.10/hr per Phase 3.5)
  amount_cents  numeric(20, 6) NOT NULL
  recorded_at   timestamptz NOT NULL DEFAULT now()
```

All four are RLS-protected on `org_id` with the NULLIF policy from Phase 2.

## 6. Provisioning state machine

5 steps, each emits a `ProvisioningEvent` over the SSE channel:

| Step | Duration | Event |
|---|---|---|
| `creating_organization` | 800 ms | starts immediately on POST |
| `allocating_host` | 1200 ms | |
| `provisioning_datacenter` | 1500 ms | |
| `deploying` | 1500 ms | |
| `ready` | 0 ms (terminal) | final event, sets `ready_at`, `status='ready'` |

Total ~5 s. The animation timings are deliberately a hair over a second each so the user perceives genuine work without it feeling slow.

State is persisted to `workspaces.provisioning_step` after each transition so a page refresh resumes the correct visual stage. A goroutine drives the timer; the SSE stream is fed from an in-process `sse.Broker` keyed by workspace id. If no client is listening, the state machine still progresses.

Failure path: a `Disabled` env var `WORKSPACE_PROVISION_FAIL=ratio` (e.g. `0.0`–`1.0`) makes a random fraction land in `status=error` with a synthetic message — used to demo the error state.

## 7. Billing (mocked)

### 7.1 PaymentMethod form

Web form fields: card_number (16 digits), exp_mm, exp_yyyy, cvc, postal_code, billing_email.

The LocalBillingProvider accepts any input matching basic shape rules:
- 16 digits (allow spaces).
- Future expiry.
- 3-4 digit CVC.

On success it returns a synthetic `customer_id = "cus_local_<base32>"`, `payment_method_id = "pm_local_<base32>"`, derives `brand` from BIN (4→visa, 5→mc, 3→amex, fallback "card"), and stores last4. The plaintext card number is **never persisted** — only `brand + last4 + exp`.

### 7.2 Invoices

Compute monthly invoices for org X by summing `usage_records.amount_cents` for `recorded_at IN [period_start, period_end)`. A `cron` job runs daily at 00:05 local and:
- Closes the previous month's open invoice if it exists.
- Opens an invoice for the current month if not yet open.

`POST /v1/billing/invoices/recompute` exists for dev/test (recompute current month immediately).

### 7.3 Usage metering

A cron job inside the control-plane runs every 60 seconds, queries `SELECT id, org_id FROM workspaces WHERE status='ready'`, and inserts one `usage_records` row per workspace with:
- `kind='runtime_hours'`
- `quantity = 1/60` (one minute, in hours)
- `unit_price_cents = 10` (= $0.10/hr)
- `amount_cents = quantity * unit_price_cents`

A dev env `USAGE_TICK_SECONDS=5` lets the demo accumulate visible usage faster.

## 8. HTTP surface

```
GET    /v1/workspaces                                      → 200 [Workspace]
POST   /v1/workspaces                                      → 202 Workspace (status=provisioning) — kicks off state machine
GET    /v1/workspaces/regions                              → 200 [Region]
GET    /v1/workspaces/:id                                  → 200 Workspace
GET    /v1/workspaces/:id/events                           → SSE text/event-stream of ProvisioningEvent
DELETE /v1/workspaces/:id                                  → 204 (suspends; soft delete in Phase 3.5)

GET    /v1/billing/payment-method                          → 200 PaymentMethod | 404
POST   /v1/billing/payment-method                          → 201 PaymentMethod
DELETE /v1/billing/payment-method                          → 204

GET    /v1/billing/invoices                                → 200 [Invoice]
POST   /v1/billing/invoices/recompute                      → 204 (dev-only)

GET    /v1/billing/usage?since=...&until=...               → 200 {total_cents, by_workspace:[...], by_kind:[...]}
```

All routes are inside the protected group, owner|admin only for the write paths.

## 10. Onboarding flow

1. Signup completes → `/v1/auth/signup` response includes `has_workspace: bool` (extends Phase 2 `AuthResp`).
2. Web sign-up page redirects to `/onboarding/workspace` when `has_workspace === false`.
3. `(app)/console/layout.tsx` now also checks: if user has no workspace, redirect to `/onboarding/workspace`. Idempotent.
4. The onboarding page wizard:
   - Step 1: form (name input + RegionPicker).
   - Submit → POST `/v1/workspaces`. Response includes workspace id.
   - Step 2: open EventSource on `/v1/workspaces/:id/events`. Render 5-step progress bar with check icons turning green as each event arrives. Show region badge + workspace name from the form.
   - Final `ready` event → 1-second pause → `router.push("/console")`.

## 11. Console panel

- **Sidebar**: replace the static "Workspace" heading with a `WorkspaceSwitcher` dropdown. Top item shows current workspace name + region pill. Dropdown lists all workspaces; bottom row links to `/console/settings/workspaces` (Manage workspaces).
- **Topbar**: small `WorkspaceBadge` to the left of the breadcrumb showing the region (e.g. `🇺🇸 us-east-1`).
- **Home**: extends Phase 3 Home — adds a workspace card next to the org card showing name + region + status + uptime ("Created 3h ago").
- **/console/settings/workspaces**: table of workspaces + "Create workspace" button → reuses the onboarding wizard inline.

The current workspace is stored in a `nexis_workspace` cookie (`HttpOnly=false, Path=/`) so the UI can read it client-side without a server round-trip. The control-plane reads it from the header `X-Nexis-Workspace` and validates it against the principal's org.

## 12. Acceptance criteria

1. **Onboarding gate**: a fresh signup gets bounced to `/onboarding/workspace`. Direct `GET /console` redirects there too.
2. **Provisioning animation**: SSE stream produces 5 events ending with `ready` within ~6 s. The workspace row transitions through `status` values.
3. **Region visible**: `/console` Home card shows the region; topbar shows the region pill.
4. **Workspace switcher**: user creating a second workspace can switch between them via the sidebar dropdown; the topbar badge updates.
5. **Billing form**: submitting `4242 4242 4242 4242 / 12 / 30 / 123 / 10001` creates a PaymentMethod with `brand=visa last4=4242`.
6. **Usage records**: with `USAGE_TICK_SECONDS=5`, waiting 30 seconds produces at least 5 `usage_records` rows for the workspace. `/v1/billing/usage` returns a non-zero `total_cents`.
7. **RBAC**: a member-role user gets 403 on `POST /v1/workspaces`.
8. **Logout still works**; protected pages still bounce unauthenticated users.

## 14. Risks / open items

- **SSE through the Next.js dev proxy**: control-plane SSE will pass through if EventSource hits the API directly (`http://localhost:8080`) rather than a Next API route. We'll set that pattern explicitly in `apps/web/lib/workspaces.ts`.
- **`current_workspace_id` not yet RLS-bound**: Phase 4 will add a second GUC for workspace-level isolation. Phase 3.5 keeps everything org-scoped to avoid a half-baked RLS schema.
- **Mock card number storage**: we never store the PAN. The browser sends it once over HTTPS (Phase 7) or HTTP (dev); the server validates shape and discards. The mock provider derives the BIN client- and server-side and only persists `brand + last4`.
- **Stripe webhook signature**: not used in Phase 3.5 since there's no real Stripe. The `internal/adapter/billing/stripe/provider.go` returns `ErrNotImplemented` everywhere.
- **Cron + Postgres**: the cron loop opens a fresh tx per tick to avoid holding a connection. Workspaces in `provisioning` or `error` don't accrue.
