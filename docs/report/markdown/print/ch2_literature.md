# Chapter 2: Literature Review

Nexis is assembled from tools that already exist and are already trusted in production, so the review that follows is written to separate two things that are easily confused: what the project *depends on*, and what it *extends*. This chapter therefore surveys the families of work the platform touches — Large Language Model (LLM) coding assistants, durable workflow orchestration, graph and causal root-cause analysis, and the self-healing/AIOps ecosystem — and states, tool by tool, the exact role each one plays inside Nexis. Section 2.1 presents that survey, Section 2.2 isolates the gap that none of the surveyed systems closes, and Section 2.3 states what the project claims as its own contribution against that gap.

## 2.1 Overview

Nexis is, at its core, a systems-integration project: its contribution comes not from a single new algorithm but from composing several established, well-engineered tools into a closed loop that none of them forms alone. Since intellectual honesty demands a clear account of what each tool already does, the discussion below goes tool by tool, distinguishing plain dependency from genuine extension.

**Large Language Model (LLM) coding assistants.** GitHub Copilot [1] is the most widely deployed Artificial Intelligence (AI) pair-programming tool: it completes code and, in its agent modes, drafts multi-file changes inside an editor session. Yet all of this happens inside the developer's authoring context. Copilot never observes a production incident, never checks its own output against a failing system, and never deploys anything. Nexis's Backend agent occupies that same "generate a minimal code change" niche, though what invokes it is a fault-detection pipeline rather than a keystroke, and its output is machine-validated before any human sees it.

**Durable workflow orchestration.** Temporal [2] provides durable, replayable workflow execution with automatic retry and state persistence. Nexis takes Temporal as-is, as a dependency: the entire nine-agent RecoveryPipeline runs as a single Temporal workflow, which is why every agent step survives a process restart and is recorded as a durable ActivityEvent. What Temporal does not provide is the engineering semantics layered on top: role routing, contract-violation detection, and severity classification are all Nexis's own logic.

**Graph databases for dependency analysis.** Neo4j [3] is a native graph database, and Nexis stores its code-dependency graph inside it. The Pathfinder agent walks that graph from a fault symptom to candidate root-cause nodes, forwarding hop distance and node degree as evidence. Neo4j supplies storage and traversal, nothing more; the evidence-ranking applied to the traversal results is Nexis's own code.

**Causal inference tooling.** DoWhy [4], Microsoft Research's library for explicit causal modelling with refutation tests, is the methodological reference point behind Nexis's causal-inference sidecar. It must be stated plainly, however, that Nexis does *not* fit a DoWhy structural causal model, since no interventional production data exists to fit one against. As such, the sidecar implements a documented proxy instead, ranking candidates by evidence-chain specificity, graph-structural proximity, textual overlap, and a scenario prior, with a transparent per-component confidence breakdown.

**Observability standards.** OpenTelemetry [5] standardises traces, metrics, and logs; Nexis adopts it, unmodified, as its instrumentation layer, exporting to Prometheus, Loki, and Tempo behind Grafana. It is a straightforward dependency: Nexis adds nothing to the standard itself.

**GitOps deployment.** Argo CD [6] reconciles a cluster against a Git repository and exposes Sync and Rollback operations. Nexis's DevOps agent emits Argo CD manifests, and whenever a policy-gated Service Level Objective (SLO) breach is detected, the post-deploy rollback probe calls Argo CD's real Rollback client. That is integration on Nexis's part, not an extension of Argo CD itself.

**Container runtimes.** Docker [10] is the target Application Programming Interface (API) for two components inside Nexis: the Validator's sandbox, a network-isolated, read-only, capability-dropped shadow execution of every candidate patch, and the preview-deploy engine. Podman [11] stood in for Docker in the evaluation environment, as a Docker-API-compatible runtime, and behaved identically; the substitution is reported honestly here, not hidden.

**Property-based testing.** Hypothesis [9] generates test inputs from declared properties. Nexis's Quality Assurance (QA) agent puts it to a genuinely new use, auto-generating pytest/Hypothesis suites from the incident and the Backend diff while Hypothesis itself stays unmodified. A background QA loop then replays the stored suites and raises a fresh incident on any pass-to-fail regression.

**Data lineage.** OpenLineage [8] defines an open specification for run-level lineage events. Nexis's Data Engineer agent emits OpenLineage-compatible RunEvents for every migration it proposes or applies; here too, Nexis conforms to the specification rather than extending it.

**The incident-response ecosystem.** Sentry [14], Datadog [16], and PagerDuty [15] respectively capture application errors, aggregate observability data, and route alerts to an on-call human. Nexis integrates all three as webhook-driven incident *sources* feeding the same Sentinel pipeline. The Slack API [17] is used in the opposite direction: the Approval Gate pushes a decision into Slack, where an engineer can approve or reject a validated patch with one click. A further set of platform dependencies is used exactly as documented, without modification: WorkOS for Single Sign-On (SSO) [12], Stripe for billing [13], PostgreSQL Row-Level Security (RLS) for tenant isolation [7], pgvector for knowledge-base retrieval [19], and Ollama [20], the local Large Language Model provider behind this report's live evidence. ## 2.2 Research Gap

Each tool surveyed above is strong within its own boundary, and several of them are routinely chained together in industry: Sentry alerting into PagerDuty, an on-call engineer opening an editor with GitHub Copilot, Argo CD eventually deploying the merge that follows. Moreover, what no single tool, nor any combination in common use, provides is a system that (a) models a software engineering *team* with explicit role specialisation, and (b) closes the loop from automatic fault detection to a deployed, verified fix, with human judgement concentrated at one severity-routed decision point.

This gap shows up at every seam of the conventional tool chain. GitHub Copilot generates code but never sees a production incident; it has no notion of a fault, a blast radius, or a deployment [1]. Observability platforms such as Datadog and Sentry detect and display faults with great fidelity, yet they never generate a candidate fix, let alone validate one [16, 14]. PagerDuty routes a human to the problem, but the repair itself stays entirely manual [15]. Argo CD deploys whatever a repository contains, though it authors nothing [6]. Temporal can durably orchestrate any of these steps; still, it carries no engineering semantics of its own [2]. In every case the loop breaks at the same place: between "a fault is known" and "a validated fix exists," a human performs the unaided diagnosis, authoring, testing, review, and release.

Nexis closes precisely that span, end to end. Sentinel detects a fault using a statistical-process-control rule, an Exponentially Weighted Moving Average (EWMA) baseline with a mean-plus-three-sigma breach condition, rather than a fixed threshold. Pathfinder then walks the real Neo4j dependency graph to candidate root causes, which the causal-inference sidecar ranks with a transparent confidence breakdown. The Synthesiser classifies the scenario and selects which Execution Team agents are actually needed, and the workflow enforces that routing by visibly skipping the agents not selected. The Architect, for its part, produces a structured plan whose `affected_files` contract is mechanically checked against the Backend agent's actual diff; a violation forces HIGH severity so the change can never auto-deploy unreviewed. Quality Assurance generates property-based tests from the incident and the diff [9], and the Validator then executes the patch and those tests inside a locked-down container sandbox, so no unvalidated patch ever reaches a human. Only at this final stage does the single human decision point engage, and only when severity warrants it: HIGH-severity changes require explicit review, MEDIUM-severity changes auto-approve after a 120-second window unless overridden, and trivial LOW-severity changes pass immediately. The decision itself is richer than a binary gate, since the engineer may Approve, Reject, or Modify the diff before it ships, with every terminal decision persisted for future preference learning. On approval, a real GitHub pull request is opened, and a post-deploy rollback probe watches for the regression that follows [6].

Two further properties set this apart from a merely scripted pipeline of existing tools. It may be noted, first, that role specialisation here is structural, not cosmetic: the five Execution Team agents (Architect, Backend, Quality Assurance, DevOps, Data Engineer) and the four Self-Healing Loop agents (Sentinel, Pathfinder, Synthesiser, Validator) have distinct inputs, outputs, and contracts, and the Architect's plan constrains the others. Second, the loop closes over the platform's own infrastructure too: when Nexis's preview-deploy engine fails to build or health-check a repository, that failure is inserted as a first-class incident into the very same pipeline, and "write a working Dockerfile" becomes an ordinary repair task. To the author's knowledge, no tool in common use today combines these properties in a single system.

## 2.3 Conclusion

The landscape surveyed in this chapter supplies every ingredient Nexis needs: durable orchestration [2], graph traversal [3], sandboxed execution [10, 11], property-based testing [9], GitOps delivery [6], and a mature incident-capture ecosystem [14, 16, 15]. What it does not supply is the loop between detection and repair; that is left open, for a human to close. Hence, Nexis's contribution lies not in any single new algorithm but in the demonstrated composition of these tools into a role-specialised multi-agent team that detects, diagnoses, repairs, validates, and deploys autonomously, engaging human judgement once, at a severity-routed gate. How that composition was specified, designed, implemented, and tested is the subject of the chapters that follow.
