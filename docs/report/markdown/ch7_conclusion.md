# Chapter 7: Conclusion and Future Work

## 7.1 Overview

Existing Artificial Intelligence (AI) developer tools do not close the loop between detecting a software failure and deploying a verified fix for it; this project set out to build one that does, keeping a human in the process as a single decision point rather than as the pipeline itself. The delivered platform, Nexis, realises that goal as a working, verified system, not merely as a design proposal.

The central deliverable is the nine-agent closed-loop self-healing pipeline, durably orchestrated by Temporal [2]. A five-agent Execution Team, comprising Architect, Backend, Quality Assurance (QA), DevOps (Development and Operations), and Data Engineer, carries out the engineering work. Running alongside it, a four-agent Self-Healing Loop, made up of Sentinel, Pathfinder, Synthesiser, and Validator, detects faults, localises root causes over the Neo4j dependency graph [3], sandbox-validates every candidate patch, and routes the outcome through a severity-classified Approval Gate that offers Approve, Reject, and Modify decisions. Crucially, this pipeline was not merely implemented; it was exercised live. Chapter 6 reports two complete end-to-end recovery runs against a real local language model [20]. In one, the 120-second approval window genuinely elapsed and the run was timeout-rejected exactly as the safety design intends; in the other, a detected fault moved through planning, patch generation, property-based test validation, human approval, and deployment to a Succeeded terminal state in approximately one minute and forty seconds.

Complementing the recovery pipeline is the from-scratch Docker (Podman-compatible runtime) preview-deploy engine [10], the project's second major deliverable. Given a connected repository, it clones the code, detects the technology stack, and generates a working Dockerfile when none exists, then builds and runs the container under resource limits before returning a live preview Uniform Resource Locator (URL). Build and health-check failures, too, feed back into the same self-healing pipeline as any other incident source. This, too, was proven live: a real public repository with no Dockerfile in it was cloned, containerised, built, served, verified over the Hypertext Transfer Protocol (HTTP), and cleanly stopped, all within a single recorded run.

Around these two engines sits a complete multi-tenant platform. Authentication runs on JavaScript Object Notation (JSON) Web Token (JWT) and Single Sign-On (SSO), backed by Multi-Factor Authentication (MFA) and session management [12], while Role-Based Access Control (RBAC) is enforced down to the database row via PostgreSQL Row-Level Security (RLS) [7]. Moreover, a heuristic role-recommendation engine turns audit-log evidence into explainable privilege suggestions, Stripe handles billing [13], and webhook-driven integrations tie in GitHub, Sentry, Datadog, PagerDuty, and Slack [14, 16, 15, 17]. On top of all this sits an observability surface, comprising dashboards, cost tracking, system health probes, and a hash-chained audit log, built on OpenTelemetry [5]. As documented in Chapter 6, all Go (Golang) modules, the Python causal-inference service, and the Next.js console pass their full build, vet, lint, and test suites.

## 7.2 Limitations of the Project

Academic integrity demands that the line between what was demonstrated and what was not be drawn plainly. The limitations listed below are real and known, each one a deliberate boundary rather than an oversight, and none of them is hidden behind softer wording.

- **No production credentials were exercised.** No real GitHub App or OpenAI production credentials existed in the evaluation environment used for this report. All the live evidence came instead from local Ollama models [20] and an unauthenticated clone of a public repository, so a fully credentialed production path, one ending in a real merged GitHub pull request, was not exercised end-to-end.
- **The platform is not yet live on its domain.** Although the `nexis.sh` domain has been registered, the platform itself is not yet deployed to it, so every piece of evidence in this report comes from local, native execution. Since Docker was unavailable in the build environment, Podman [11] was substituted as a runtime compatible with the Docker Application Programming Interface (API); it was shown to behave identically.
- **Fine-tuning is a manual step by design.** Real and already tested, the Reinforcement Learning from Human Feedback (RLHF) data-export pipeline persists every terminal approval decision, including engineer-edited diffs, in a form exportable as JSON Lines (JSONL). Actually submitting a fine-tuning job against that export, however, is a deliberate manual step, since it involves real money and a real external API call rather than an automated one.
- **One of twenty-seven demo scenarios is fully wired.** Twenty-seven curated fault scenarios are listed in the Live-Demo console, and of these, only one is wired end-to-end to a real fixture and classification path at present. As such, the remaining twenty-six are User Interface (UI)-complete but still backend-pending.
- **The causal ranking is a proxy, not a fitted causal model.** Root-cause candidates are ranked by the causal-inference sidecar through an honest statistical and graph-structural scoring method, with a transparent per-component confidence breakdown attached to each ranking. It is explicitly not a fitted DoWhy structural causal model [4]; no interventional production data exists against which such a model could be fitted, and claiming otherwise would be an overstatement.
- **A known unrelated bug was left unfixed.** During evaluation, a pre-existing bug turned up in the workspace-onboarding progress poller, a 404 returned from `/v1/workspaces/{id}/events`, and it was intentionally left unfixed as out of scope. The workspace itself, regardless, still provisions successfully on the server side.
- **No formal load testing was performed.** As noted in Chapter 6, no formal concurrent-load performance benchmark was run, and the latencies reported come from single-run live executions rather than a controlled load harness.

## 7.3 Future Work

Each item that follows is grounded in the existing architecture and reflects a concrete next step, not a generic aspiration.

- **Credentialed production deployment.** Deploy the platform to the registered `nexis.sh` domain behind a real GitHub App installation and a paid OpenAI account, so that the full production path (authenticated clone, real pull-request creation, real merge-triggered redeploy) is exercised end-to-end with production credentials.
- **Complete the scenario library.** Wire the remaining twenty-six Live-Demo scenario cards to real fixtures and classification paths, which would extend the existing eleven-scenario fault-injection library across the application, database, deploy, observability, and security categories it already enumerates.
- **Finer-grained Sentinel baselines.** At present, the Sentinel's statistical spike rule maintains its Exponentially Weighted Moving Average (EWMA) mean and variance baseline per organisation. Extending this to per-(organisation, service) baselines would thus stop a noisy service from masking a quiet one.
- **A fitted causal model.** Once production incident data with genuine interventions has accumulated, a real DoWhy structural causal model [4] should be fitted and evaluated against the current graph-evidence proxy, which was designed from the outset to be replaceable.
- **Execute a fine-tuning run.** When the accumulated RLHF export contains enough approve/reject/modify examples, the next step is to submit an actual fine-tuning job against it and see whether the tuned model reduces rejection and modification rates at the approval gate.
- **Real preview subdomains.** Adding a reverse-proxy layer (for example Traefik) in front of the deploy engine would let preview deployments receive stable per-project subdomains instead of `localhost` ports, a prerequisite for sharing preview URLs beyond the local machine.
- **Formal load benchmarking.** Run a controlled concurrent-load benchmark against the control plane and the recovery pipeline to characterise throughput, queue behaviour under simultaneous incidents, and Temporal worker saturation.
- **Human-subjects usability study.** The planned NASA Task Load Index (NASA-TLX) cognitive-workload study [18] with external participants is yet to be conducted; the survey instrument itself is already integrated into the post-incident flow, so what remains is recruitment and analysis rather than implementation.

## 7.4 Conclusion

The central claim of this report is deliberately narrow and deliberately strong: a software fault can travel from automatic detection, through multi-agent diagnosis, patch generation, and sandboxed validation, past a single human approval decision, and on to a deployed fix, all inside one continuous, durable, observable pipeline. That claim is not asserted; it is demonstrated with reproducible, live evidence. One recorded run shows the loop refusing to proceed when its human gate was not answered in time, while another shows that same loop carrying a real fault to an approved, deployed resolution in under two minutes, with every agent step, token count, and decision recorded in a durable timeline. The preview-deploy engine carries the same principle over to infrastructure, turning its own build failures into self-healing targets. Equally important, though, is what this report declines to claim. In this regard, Section 7.2 sets out that honest accounting in full: local models rather than production credentials, a registered but not yet live domain, a proxy in place of a fitted causal model, and one wired demo scenario out of twenty-seven. None of this is a list of apologies; it is part of the project's rigour, since the boundary of the evidence has been drawn exactly where the evidence stops. Within that boundary, Nexis stands as a complete, working demonstration that closed-loop fault recovery, gated by a single human decision point, is buildable today.
