# SQA Audit — 2026-05-14

## Summary

Read-only SQA / security sweep of `services/control-plane` (Go, chi, pgxpool,
Temporal) and `apps/web` (Next.js 16, React 19). The repo carries solid
foundations (RLS plumbing, HMAC-chained audit log, per-tenant webhook secrets,
constant-time Slack signature compare, defence-in-depth org_id filters) but
also ships **six concrete security gaps** that are independent of the
"dead-wiring" thread already documented in `2026-05-14-backend-audit.md`:
(1) **unbounded body reads** on every JSON endpoint (DoS),
(2) **dead handlers** that compile in but are never mounted —
`SeedSample`, `NASATLXSubmit`, `SentinelTrigger`, `OrgStats`, `SentryProbe`,
`AdminEvalExport`, `InviteCodesList`, `InviteCodesRevoke` — shipping as un-callable code,
(3) **audit-chain race** between concurrent writers in the same org,
(4) **err.Error() leakage** in 60+ handler 500-paths (table/column names land in the wire),
(5) **`activity_events.kind` column doesn't exist** — every authenticated hit on
`/v1/workspaces/{ws}/agents` 500s,
(6) **No CREATE INDEX CONCURRENTLY anywhere** — `0024_projects.up.sql` takes ACCESS EXCLUSIVE locks across `workflow_runs`, `incidents_raw`, `approvals`,
`webhook_deliveries` simultaneously.

**Severity counts:** Critical 5 · High 9 · Medium 11 · Low 8.

## Critical (security / data-leak / multi-tenant violation)

### F-1: Unbounded body read on every JSON endpoint — process-memory DoS

**Where:**
- `services/control-plane/internal/transport/http/handler/auth.go:138` (`decodeBody`: `json.NewDecoder(r.Body)`, no `http.MaxBytesReader`).
- `services/control-plane/internal/transport/http/handler/webhooks.go:185, 289` (`io.ReadAll(r.Body)` with no `io.LimitReader`).
- `services/control-plane/internal/transport/http/handler/sentry_probe.go:46` (same).
- `services/control-plane/internal/transport/http/handler/integrations.go:75` (`json.NewDecoder(r.Body).Decode` direct, bypasses `decodeBody`).
- `services/control-plane/cmd/server/main.go:477-484` — `http.Server` has no `MaxHeaderBytes` override.

**Impact:** any unauthenticated route (`/v1/auth/signup`, `/v1/auth/login`,
`/v1/auth/magic`, every `/v1/webhooks/{provider}/{org_id}` mount, the
Datadog/PagerDuty webhook-by-query mounts, `/v1/integrations/slack/interactivity`
when wired) accepts an arbitrarily large body that streams into RAM. With the
configured `ReadTimeout: 30s`, an attacker on a 1 Gbps link can push ~3.75 GB
per request, repeated until OOM. Webhook routes are the worst — `org_id` is a
URL param so the attacker doesn't even need credentials. Slack interactivity
DOES cap at 1 MiB (`slack_interactivity.go:78`) — that's the one outlier and
the pattern to copy.

**Repro:** `curl -X POST -H 'Content-Type: application/json' --data-binary @<huge.bin> http://host/v1/webhooks/sentry/<any-uuid>`.
The handler buffers the body in `io.ReadAll` BEFORE the per-tenant secret lookup,
so HMAC failure does NOT save the host from OOM.

**Recommendation:** wrap every body read in `http.MaxBytesReader(w, r.Body, N)`
(suggest 1 MiB for JSON endpoints, 256 KiB for `/v1/auth/*`, 64 KiB for
`/v1/me/preferences`). For webhooks the per-provider cap should be looser
(GitHub PRs commonly exceed 256 KiB) — 1 MiB is reasonable. Set
`MaxHeaderBytes: 16384` on the `http.Server` for symmetry.

### F-2: `activity_events.kind` does not exist — every `/v1/workspaces/{ws}/agents` hit 500s

**Where:** `services/control-plane/internal/transport/http/handler/agents.go:528-535`. Migration `migrations/0009_phase4_workflows.up.sql:36-40` defines `status text` with values `started|succeeded|failed|retrying|timed_out`. There is NO `kind` column.

**Impact:** the first authenticated user who lands on `/console/agents`
crashes the endpoint with `column "kind" does not exist`. The fix was flagged
as F-3 in `2026-05-14-backend-audit.md` and remains unmerged. Confirmed
present as of this audit by grep on `kind='finish'` in `agents.go:528-535`.

**Repro:** boot a clean stack, log in, navigate to `/console/agents`.

**Recommendation:** replace `kind='finish'` with `status IN ('succeeded','failed','timed_out')` in all 5 spots. The author intended "finish frame" semantics; the schema already names it `status`.

### F-3: Webhook `org_id` URL parameter is not validated — RLS GUC accepts any string

**Where:** `services/control-plane/internal/transport/http/handler/webhooks.go:175, 217`. `orgID := chi.URLParam(r, "org_id")` is passed verbatim to `SELECT set_config('app.current_org_id', $1, true)`.

**Impact:** the GUC is typed `text`; the RLS policy casts it via `NULLIF(current_setting(...,true),'')::uuid` so a non-uuid string lands as NULL and silently bypasses the tenant filter, OR the cast raises (depending on policy order). The webhook then processes a "delivery" against an unknown org_id, persisting a row in `webhook_deliveries` (per F-15 in backend audit, GitHub falls back to a default secret here). The org_id is also written verbatim into the audit/delivery row, polluting the dashboard. With `?org=` query (`WebhookByQuery`) the same applies to Datadog + PagerDuty.

**Repro:** `curl -X POST http://host/v1/webhooks/github/<not-a-uuid>` returns 401 (HMAC mismatch) but the path is reachable; with a known fixture default secret, the body gets accepted, writes a row with malformed org_id.

**Recommendation:** validate `org_id` is a UUID in both `Webhook` and `WebhookByQuery` (chi has `?org={org_id:[0-9a-f-]+}` route patterns; or `uuid.Parse(orgID)` at the top of the handler). Same for the `?org=` query.

### F-4: Audit-log chain has no per-org lock — concurrent writes break HMAC integrity

**Where:** `services/control-plane/internal/adapter/audit/hmac_writer.go:54-107`. The `Write` flow is `SELECT MAX(row_hash)` → compute new `row_hash` → `INSERT`. There is no `FOR UPDATE`, no `pg_advisory_lock(org_id_hash)`, no UNIQUE constraint on `(org_id, prev_hash)`.

**Impact:** two concurrent audit writes in the same org (e.g. an admin clicks
"connect integration" while a workflow records `approval.decided`) both read
the same `prev_hash` and INSERT with the SAME `prev_hash`. The chain forks.
`audit.Verify` then fails on the next walk because every fork past the split
has the same `prev_hash` parent but only one is reachable via "latest row".
This is silent until someone runs `/v1/audit/verify`.

**Repro:** `for i in {1..50}; do curl -X POST -H @cookies /v1/apikeys & curl -X POST -H @cookies /v1/integrations/sentry/connect & done; wait`. `GET /v1/audit/verify` then reports a chain break.

**Recommendation:** wrap the `SELECT prev + compute + INSERT` in a transaction that takes `SELECT pg_advisory_xact_lock(hashtext(org_id::text))` first, so only one writer per org holds the slot. Cheap (transaction-scoped, auto-released), bounded by org count. Or add a unique constraint `(org_id, prev_hash)` so a parallel insert raises a 23505 the caller can retry.

### F-5: 60+ handlers leak raw `err.Error()` in 500 responses — DB schema disclosure

**Where:** grep `httpJSON.*err.Error()` across `internal/transport/http/handler/`:
- `agents.go:191, 231, 244` — pgx scan errors expose table aliases (`ae`, `wr`) and column names.
- `billing.go:71, 125, 181, 195, 213, 240` — `usage_records.amount_cents` cast errors land in clients.
- `invites.go:56, 82, 114, 130, 159` — same.
- `preferences.go:47, 79`, `ops_cost.go:62, 81, 88, 106, 113`, `ops_knowledge.go:47, 65, 76`, `audit.go:80, 99` — same.
- `pipelines.go` SSE — `httpJSON(w, http.StatusInternalServerError, map[string]string{"error": err.Error()})` after the Temporal Start error path.

**Impact:** a probing attacker sends malformed bodies to trigger pgx errors
(`ERROR: invalid input syntax for type uuid: "x" (SQLSTATE 22P02)`) or hits an
intentionally over-large pagination param to elicit
`SELECT … FROM activity_events ae JOIN workflow_runs wr ON …` text in the
response. This is enough to map the entire schema without DB access.
`integration.connected` Connect errors (`integrations.go:90`) bubble up
provider-specific failures with credential-adjacent context.

**Repro:** `curl -b cookies "http://host/v1/projects/not-a-uuid/recovery-policy"` returns the SQL-level cast error text in the body.

**Recommendation:** introduce a single `httpInternalError(w, err, op)` helper that `slog.Error`s the full err and writes a fixed `"error":"internal"` body with the request id. Audit + ops surfaces already follow this for some routes; make it universal.

## High (correctness, audit-gap)

### F-6: 8 handlers are defined, audited, exported — but never mounted

**Where:** `services/control-plane/internal/transport/http/handler/{seed_sample,nasa_tlx,sentinel_admin,sentry_probe,admin_eval_export,org_stats,invite_codes}.go`.

These handlers compile cleanly, write to `audit_log`, exist in `Deps` fields
on `Deps` (`server.go:97-105`), and are EXPORTED at the package boundary —
but the router never wires them. Grep confirms zero `r.Post("/v1/nasa-tlx",
...)`, no `/v1/admin/sentinel/trigger`, no `/v1/integrations/sentry/probe`,
no `/v1/invite-codes`, no `/v1/me/org-stats`, no `/v1/admin/eval/export`.

**Impact:** twofold:
1. **Public-beta features documented in `Deps` doc-comments simply don't ship.**
   The NASA-TLX survey, sentinel admin trigger, sentry probe, BetterStack-style
   integration log export, and the org-stats panel all advertise an HTTP
   surface that doesn't exist. Operators discovering this from the dashboard's
   404 banners can't tell whether it's a routing bug or a feature flag.
2. **The handlers carry input validation, audit emits, and ServiceUnavailable
   guards that suggest they were intended to ship.** Half the surface that
   `Deps.OrgStats`, `Deps.InviteCodes`, `Deps.NASATLX`, `Deps.Sentinel`,
   `Deps.SystemHealth` reference is unused dead wiring on the call sites.

**Recommendation:** for each handler, decide (a) mount it, or (b) delete the
file + the `Deps` field. Don't leave audited-but-unreachable code in the
binary — at minimum it lies to grep-driven security reviews about what the
service exposes.

### F-7: `IntegrationsConnect` bypasses `decodeBody` — no DisallowUnknownFields, no body cap

**Where:** `services/control-plane/internal/transport/http/handler/integrations.go:73-78`.

**Impact:** `json.NewDecoder(r.Body).Decode(&raw)` accepts unknown keys (so a
typo like `{"installation_idd": "...", "config": {...}}` silently drops the
typoed key while still triggering Connect with `{}`). The body is unbounded.
For owner|admin only, but still — every other JSON handler enforces both via
`decodeBody`. This one was hand-rolled to support the `{config: {...}}`
wrapper form, but the wrapper-detect path can be done after `decodeBody`.

**Recommendation:** route through `decodeBody` against a `dto.ConnectRawReq { Config map[string]any; ... }` then inline the wrapper detection.

### F-8: `X-Forwarded-For` parser picks the closest-proxy IP, not the originating client

**Where:** `services/control-plane/internal/transport/http/handler/webhooks.go:80-95`.

```go
for i := len(parts) - 1; i >= 0; i-- {
  ...
  return ip
}
```

**Impact:** the comment says "the closest non-private address" but the loop
walks right-to-left and `return`s on the first non-empty match — which is the
LAST entry (rightmost, the closest proxy). XFF chain ordering is
`client, proxy1, proxy2, ...` so the rightmost entry is the host that
delivered the request to the control-plane, NOT the client. Audit rows
(`webhook_deliveries.source_ip`) therefore record the immediate-upstream proxy
in every deployment with a reverse proxy in front. Attackers can also forge
XFF freely (no allowlist of trusted proxies).

**Recommendation:** maintain a trusted-proxy CIDR allowlist (`cfg.TrustedProxyCIDRs`) and only honor XFF when `r.RemoteAddr` is inside it. Within a trusted XFF chain, the leftmost (parts[0]) entry is the originating client. Without a trusted upstream, use `r.RemoteAddr` only.

### F-9: `verifyInstallState` uses `==` instead of `subtle.ConstantTimeCompare`

**Where:** `services/control-plane/internal/transport/http/handler/integration_oauth.go:96-102`.

**Impact:** the OAuth state CSRF check is `c.Value == state` (Go string ==).
32-byte base64-url tokens (43 chars) mean a timing attack is bounded but not
impossible across the network. Slack interactivity uses
`subtle.ConstantTimeCompare` (`integration/slack/interactivity.go:106`) —
adopt the same pattern.

**Recommendation:** `subtle.ConstantTimeCompare([]byte(c.Value), []byte(state)) == 1`.

### F-10: Webhook ingestion has no idempotency / replay protection

**Where:** `services/control-plane/internal/transport/http/handler/webhooks.go:171-258` (`Webhook` + `WebhookByQuery`). Each provider's `HandleWebhook` (sentry/github/datadog/pagerduty) verifies HMAC but doesn't track delivery IDs.

**Impact:** GitHub sends `X-GitHub-Delivery: <uuid>`, Sentry sends `Sentry-Hook-Resource` + envelope `id`, PagerDuty sends `X-PagerDuty-Webhook-Id`, Datadog re-fires on its own retry policy. None of these are deduped. A doubly-delivered webhook (e.g. retry after a 502 from `IncidentSink.Insert` racing with the retry) creates two incidents and two `webhook_deliveries` rows. With F-1 in `2026-05-14-backend-audit.md` fixed (sentinel router live), each duplicate triggers a recovery pipeline — wasteful at best, dangerous at worst (concurrent apply on the same root cause).

**Recommendation:** add a `webhook_idempotency` table keyed on `(provider, source_event_id, org_id)` with a `recvd_at` UNIQUE constraint. Check before dispatching; insert after successful dispatch (in the same tx). For GitHub, key on `X-GitHub-Delivery`.

### F-11: Webhook handlers do not enforce `Content-Type` — non-JSON bodies pass HMAC and crash JSON probe

**Where:** `services/control-plane/internal/transport/http/handler/webhooks.go:101-115` (`bodyAsJSONForAudit`). The handler's audit-row path always tries `json.Unmarshal`, silently falls back to `{"raw_head_utf8": ...}` on failure.

**Impact:** an attacker who steals the per-tenant HMAC secret (or hits a tenant in F-15's defaultSecret race window) can post a binary blob that signs validly but isn't JSON. The downstream `p.HandleWebhook` then tries to `json.Unmarshal` and rejects, but the `webhook_deliveries` row is already written with `raw_head_utf8` containing the binary. Repeated, this poisons the dashboard table with garbage.

**Recommendation:** require `Content-Type: application/json` (or the provider-specific equivalent) at the top of the handler; reject with 415 otherwise. Sentry / GitHub / Slack / Datadog / PagerDuty all set it.

### F-12: Body decode in webhooks is performed BEFORE provider registry lookup

**Where:** `services/control-plane/internal/transport/http/handler/webhooks.go:185-193`. The handler reads the full body, then checks `reg.Get(providerName)` — if the provider name is unknown the body has already been buffered.

**Impact:** unauthenticated DoS — `for i in {1..N}; do curl -X POST --data-binary @big.bin /v1/webhooks/fakeprovider/<orgid>; done` exhausts memory before the 404 short-circuit fires. Same shape on the WebhookByQuery path.

**Recommendation:** swap the order — `reg.Get` first, then body read with `io.LimitReader`. The provider name comes from chi URL params (`webhooks.go:174`) which are bounded.

### F-13: `IntegrationsConnect` doesn't enforce a provider allowlist on body shape

**Where:** `services/control-plane/internal/transport/http/handler/integrations.go:88` — `cfg` (a `dto.ConnectReq = map[string]any`) is handed verbatim to `p.Connect(...)`. Each provider extracts what it wants from the map, but there is no schema check at the HTTP boundary.

**Impact:** the request body can carry attacker-controlled keys (e.g. `{"installation_id": "...", "webhook_url": "http://attacker/exfil"}`) that some provider's Connect uses without sanitisation. Slack's Connect at `slack/provider.go:135` reads `webhook_url` from the map and POSTs to it (`postRaw`). A malicious owner|admin (or compromised session for an org with no Slack integration yet) can use `IntegrationsConnect` to make the control-plane POST to an arbitrary HTTP URL — SSRF.

**Repro:** `curl -X POST -b cookies -H "Content-Type: application/json" -d '{"webhook_url": "http://169.254.169.254/latest/meta-data"}' /v1/integrations/slack/connect`. Slack's legacy webhook path posts to the URL with the well-known body `{"text": "Nexis connected"}`. Cloud metadata returns 200 → Connect succeeds, blob persisted with URL.

**Recommendation:** validate `webhook_url` is `https://hooks.slack.com/services/...` (the canonical incoming-webhook host) before posting. More broadly, every provider's Connect should validate URL inputs against a host allowlist.

### F-14: Slack Connect `postRaw` SSRF — no host check, no scheme check

**Where:** `services/control-plane/internal/adapter/integration/slack/provider.go:413-436`. The legacy webhook URL is taken from `cfg["webhook_url"]` (provided by the caller) and POSTed to without validation.

**Impact:** see F-13. The legacy flow exists for Phase 3 compatibility; the OAuth v2 flow is the recommended path. A malicious admin can use the Connect endpoint to probe the internal network or exfil to a webhook the attacker controls.

**Recommendation:** drop the legacy webhook_url path now that OAuth v2 is wired (`integration/slack/real.go:89-102`). If kept, gate the URL on `https://hooks.slack.com/services/T...`.

## Medium

### F-15: Migrations take ACCESS EXCLUSIVE locks; zero `CREATE INDEX CONCURRENTLY`

**Where:** `services/control-plane/migrations/*.up.sql`. Total `CREATE INDEX` statements: 56. Total `CREATE INDEX CONCURRENTLY`: 0.

The worst offender is `0024_projects.up.sql:52-70`:
1. `CREATE TABLE projects` (fast — empty table).
2. `CREATE INDEX idx_projects_org_workspace`, 4 more — all on the new table, OK.
3. **`ALTER TABLE workflow_runs ADD COLUMN project_id uuid REFERENCES projects(id)`** — takes ACCESS EXCLUSIVE on `workflow_runs` (a hot, large table) WHILE every reader is blocked.
4. Same for `incidents_raw`, `approvals`, `webhook_deliveries`.
5. `CREATE INDEX idx_workflow_runs_project ON workflow_runs (...)` — another ACCESS EXCLUSIVE blocking window.

**Impact:** applying `0024` against a production-shaped DB pauses every read+write to those tables for the duration of the migration. Estimated impact at 1M+ workflow_runs: 30-120s of full unavailability. Postgres `lock_timeout` is not set so the migration will wait for foreign-key validation.

**Recommendation:**
1. Two-phase migration pattern: `ADD COLUMN project_id uuid NULL` (cheap — only catalog update), then `ALTER COLUMN ... ADD CONSTRAINT ... NOT VALID` for the FK (skips full-table validation), then `VALIDATE CONSTRAINT` in a separate migration during low-traffic windows.
2. `CREATE INDEX CONCURRENTLY` always — it's slower but doesn't block writers. The downside (cannot run in a tx) is fine for migration scripts that run one statement at a time.
3. Set `SET LOCAL lock_timeout = '30s'` at the top of every migration so a hung lock bails instead of stalling the whole stack.

### F-16: `WebhookByQuery` accepts `?org=<orgID>` with no validation — same DoS surface as F-1

**Where:** `services/control-plane/internal/transport/http/handler/webhooks.go:277, 321`.

**Impact:** anyone can POST to `/v1/integrations/datadog/webhook?org=<anything>` and the handler tries to pin `app.current_org_id` (works for any string), then look up the per-tenant secret. With F-15 from backend audit (Datadog defaults to "fail open" when no secret), a malicious payload lands in the IncidentSink for any orgID the attacker writes in the URL.

**Recommendation:** validate `?org=` is a UUID; verify it matches a row in `integrations` (i.e. the tenant has Datadog connected) BEFORE reading the body.

### F-17: 22 `as never` / `as unknown as never` casts on Next.js typed routes

**Where:** confirmed in `2026-05-14-frontend-audit.md` F-15 (count: 20). Re-verified at 22 today across `components/console/Sidebar.tsx`, `components/console/Topbar.tsx`, `RecoveryPipelineMini.tsx`, `SystemStatusPanel.tsx`, `KpiCard.tsx`, etc.

**Impact:** TS strict-mode escape hatch. Every dynamic href bypasses the
typed-route check, so refactoring a route (e.g. `/console/incidents/[id]` →
`/console/recoveries/[id]`) won't surface a TS error at any of the call sites.
A search-and-replace miss becomes a runtime 404.

**Recommendation:** prefer `Route` cast from `next` (already imported in
several call sites). For dynamic hrefs add a `// typed-route: dynamic`
comment so future readers know the cast is intentional.

### F-19: 4 tables under `*_repo.go` allow per-tenant UPDATE/DELETE without org_id WHERE — RLS-only enforcement

**Where:**
- `services/control-plane/internal/adapter/repo/projects_repo.go:262, 272-274` — `UPDATE projects SET … WHERE id = $1` (no org_id filter, app pool, relies on RLS).
- `services/control-plane/internal/adapter/repo/workflows_repo.go:71-78` — `UPDATE workflow_runs … WHERE id = $1`.
- `services/control-plane/internal/adapter/repo/workspaces_repo.go:79-91` — `UPDATE workspaces … WHERE id = $1` (admin pool, **no RLS**, comment acknowledges).
- `services/control-plane/internal/adapter/repo/billing_repo.go:91-92` — `DELETE FROM payment_methods WHERE org_id=$1` (good).

**Impact:** workspaces.Suspend (`workspace/service.go:182-184`) calls
UpdateStatus which runs on the admin pool — no RLS, no org_id filter. The
handler's pre-check (`workspaces.go:132`) protects against direct
exploitation, but it's TOCTOU-shaped: an attacker race against admin-pool
visibility could in principle expand the window. Same shape for projects'
Update — RLS is the only defence; a future maintainer who switches from app
pool to admin pool (for a "system path") opens cross-tenant writes.

**Recommendation:** add explicit `WHERE id=$1 AND org_id=$2` to every UPDATE,
even when running under RLS. Defence-in-depth — the comment-only pattern is
fragile.

### F-21: Slack `Decide` path doesn't emit `approval.decided` for the actor — audit gap

**Where:** `services/control-plane/internal/transport/http/handler/slack_interactivity.go:118` → `services/control-plane/internal/adapter/approval/signaler.go:85-110` → `services/control-plane/internal/adapter/approval/service.go:118-130`.

The `Service.RecordDecision` does emit `audit.Write` (`service.go:124`), but
the actor on that row is whatever `domain.Principal{OrgID, UserID: sig.DecidedBy}`
the Decide payload synthesises. The Slack-side `DecidedBy = in.Principal.UserID`
(`signaler.go:101`), and the SignalerService Decide path takes `in.Principal`
from a `DecideInput` that the Slack handler does NOT populate
(`slack_interactivity.go:118` calls `approvals.Decide(ctx, runID, decision, actorEmail)`
which is a DIFFERENT method signature than `SignalerService.Decide(ctx, DecideInput{...})`).

The narrow `SlackApprovalsService` interface (`slack_interactivity.go:46`) only
takes `actorEmail string`. The adapter that bridges this onto `SignalerService`
must (a) resolve the email to a `domain.Principal{UserID, OrgID, Role}` before
calling `Decide`, or (b) the audit row records `actor=""`. There is no such
adapter in the repo today (the comment at `slack_interactivity.go:37-38`
explicitly defers it).

**Impact:** when the slack interactivity route is wired, every approval
decided from Slack carries an empty `actor` field in `audit_log`. The audit
table CSV export shows "decided by ?" for these — compliance ambiguity.

**Recommendation:** ship the adapter that resolves `payload.User.Email` to a
local `users.id`, or surface the email in the audit metadata as a fallback.

### F-22: Magic-link token consumption doesn't emit a `user.magic_failed` audit row

**Where:** `services/control-plane/internal/transport/http/handler/auth.go:287-310`. On a success path the handler audits `user.magic_consumed`; on a failure path it returns 401 with `mapAuthError(err)` but does NOT write `user.magic_failed`. Same for `Signup` (no `user.signup_failed` on duplicate email).

**Impact:** brute-force enumeration of magic tokens (or signup emails) leaves
no trail. The compliance audit log skips the failure half of every auth
attempt.

**Recommendation:** audit both branches with `user.signup_failed` / `user.login_failed` / `user.magic_failed`. Slogger already logs these; mirror to `audit_log`.

### F-23: No rate limiting anywhere — magic-link / login / webhook brute-force open

**Where:** zero hits for `ratelimit`, `rate.Limit`, or any throttling middleware in `services/control-plane/internal/transport/http/`.

**Impact:** `/v1/auth/login` accepts unbounded parallel attempts. Magic-link
tokens are 32 random bytes (`local/provider.go` — not re-read here, taken
from prior reviews) — strong enough that brute force is impractical, but the
absence of rate limiting on `/v1/auth/login` (password-mode) means credential
stuffing has no friction. Same for `/v1/webhooks/{provider}/{org_id}` — an
attacker can DoS the per-tenant HMAC fast path.

**Recommendation:** add a token-bucket middleware keyed on `(IP, route)`. Free
choice of library; the simplest is `golang.org/x/time/rate` with an in-memory
LRU of buckets. For webhook routes the bucket should be per-`(provider, org_id)`
so a noisy customer doesn't starve others.

### F-24: SSE handlers don't enforce a per-connection time bound — slow-loris vector

**Where:** `services/control-plane/internal/transport/http/handler/pipelines.go:302-399` (`PipelineEvents`), `workspaces.go:157-178` (`WorkspaceEvents`), `ops_activity.go:85+` (`OrgActivityStream`).

The handlers explicitly clear the write deadline (`rc.SetWriteDeadline(time.Time{})`) so the 60s WriteTimeout doesn't sever the stream. There is no replacement bound — the connection lives until the client disconnects.

**Impact:** an attacker holds thousands of SSE connections open, never reads,
exhausts the connection pool. The chi `Timeout` middleware (60s) is bypassed
for these routes. The `IdleTimeout: 120s` on the server is the only fallback,
and it only fires if the underlying TCP connection idles.

**Recommendation:** add a max-connection-age per SSE handler (e.g. 5 minutes); on expiry write a final frame `event: close\ndata: max-age\n\n` and close.

### F-25: `decodeBody`'s 400 swallows the underlying error — clients can't tell "missing field" from "unknown key"

**Where:** `services/control-plane/internal/transport/http/handler/auth.go:140-144`.

**Impact:** debugging from the dashboard is brittle. Any 400 says "invalid request body" — operators have no signal whether the payload was rejected for unknown-fields, type mismatch, or missing-required. With `DisallowUnknownFields()` and `Decode` co-located, the err message carries the column name; surface it (without leaking internal types).

**Recommendation:** when `errors.As(err, &json.UnmarshalTypeError)` extract `field`; when err contains `"json: unknown field"` extract the field; return `{"error": "invalid body", "field": "<name>"}`.

### F-26: `lib/auth.ts` echoes the TOTP secret to clients in dev — gate on env

### F-27: `nasa_tlx_repo` audit metadata doesn't include subscale scores

**Where:** `services/control-plane/internal/transport/http/handler/nasa_tlx.go:101-103`. The audit row carries `{"recovery_run_id": "..."}` only — the actual scores (which the operator wants in the audit log for compliance) are NOT in `audit_log.metadata`. They land in `nasa_tlx_responses` only.

**Recommendation:** mirror the 6 subscales into the audit metadata so the audit log is self-contained.

### F-28: `validateSelectors` in projects allows trailing whitespace in `github_repo` / Sentry slugs

**Where:** `services/control-plane/internal/usecase/projects.go:407+`. `validateSelectors` (not read in full) likely does not strip+normalise. The DB columns are `text` — accept anything; the GitHub adapter then calls the GitHub API with a mangled repo name and gets a 404 at runtime.

**Recommendation:** `strings.TrimSpace` + length cap (255) + character-class check on every selector field before persisting.

### F-29: `slugify` doesn't bound output length

**Where:** `services/control-plane/internal/usecase/projects.go:425+`. `slugify(in.Name)` runs unbounded — a 4 KB project name becomes a 4 KB slug. The DB has no length CHECK on `slug`.

**Recommendation:** cap slug at 64 chars (the chosen UI display width), error on collision rather than producing `-XX` suffixes that exceed 80 chars.

### F-30: Stripe SetupIntent confirm doesn't verify the intent's currency matches the org's tier

**Where:** `services/control-plane/internal/transport/http/handler/billing.go:142-170`. The confirm endpoint accepts the SetupIntent id from the client and trusts it.

**Recommendation:** look up the SetupIntent server-side via Stripe SDK and verify `currency` + `customer` match the org's row before persisting the payment method.

### F-31: `bodyAsJSONForAudit` truncates at 32 KB but doesn't sanitize PII

**Where:** `services/control-plane/internal/transport/http/handler/webhooks.go:97-115`. The full body becomes a `jsonb` in `webhook_deliveries.payload`. GitHub PR bodies, Sentry stack traces, Slack message text all land verbatim. GDPR-sensitive (user email in commit author, comment author full text, etc.).

**Recommendation:** keep a separate `webhook_payloads` store with a retention policy (e.g. 30 days); keep only a `payload_size` + sha256 in `webhook_deliveries`. Or scrub known PII fields (email, name) before persisting.

### F-32: Tests use `cookies.curl(...)` instead of `.Net/http` cookies — e2e bash scripts can desync

**Where:** `tests/e2e/full_journey.sh:46, 88, 101, 109` and `full_flow.sh:43, 49, 56, 69`. The scripts pass `-c $COOKIES` (write) on login and `-b $COOKIES` (read) on every subsequent call. This works, but the scripts don't check `Set-Cookie` rotation (the server can refresh the session cookie on each request) and don't refresh the cookie file. If the auth provider ever rolls the session cookie mid-script, all subsequent calls 401.

**Recommendation:** use both `-b $COOKIES -c $COOKIES` on every curl so updates land.

### F-33: `tests/e2e/full_journey.sh` retries on `null` workspace ID by failing — flake on cold boot

**Where:** `tests/e2e/full_journey.sh:55-56`. `WS=$(jq -r '.[0].id')` on an empty array returns `null`. The script fails immediately. On cold boot the seed workspace may take 5-10s to provision (the state machine in `workspace/service.go:127-135` runs in a goroutine).

**Recommendation:** poll `/v1/workspaces` with a 30s budget before failing.

## Recommended new E2E scenarios

1. **Cross-tenant denial — webhook ingest with foreign org_id.** Two orgs A and B; org A has Sentry connected with a known secret. Send a Sentry webhook to `/v1/webhooks/sentry/<B-org-id>` signed with A's secret. Expect 401 (B has no Sentry row, the lookup fails on `repo.Get`). Bonus: assert no `webhook_deliveries` row for B beyond the rejection log.

2. **Audit-chain concurrency.** Spawn 50 parallel `/v1/integrations/{provider}/probe` calls in the same org session. After completion, hit `/v1/audit/verify`. Expect OK. Today this fails per F-4.

3. **Body-size DoS.** `curl -X POST --data-binary @1gb.bin /v1/auth/signup`. Expect 413 Payload Too Large within 1s. Today this fills the server's RAM.

4. **`/v1/workspaces/{ws}/agents` smoke.** Log in, hit the endpoint. Expect 200 with a JSON array. Today this 500s (F-2).

5. **Dead-route surface.** Hit each of `/v1/nasa-tlx`, `/v1/admin/sentinel/trigger`, `/v1/integrations/sentry/probe`, `/v1/invite-codes`, `/v1/me/org-stats`, `/v1/admin/eval/export`. Expect either 200 or a documented 404 with a feature-flag banner — not silent 404 against a service that compiles in the handler.

6. **OAuth state CSRF replay.** Save the `nexis_oauth_state` cookie after `/v1/integrations/github/install`. Replay the callback with the saved cookie + a fresh randomly-chosen `installation_id`. Expect rejection on either CSRF mismatch or a "state already consumed" guard. Today the cookie is one-shot, but the timing-attack window on the `==` compare (F-9) is theoretically observable.

7. **Concurrent project create at the cap.** Two parallel POSTs at the workspace's cap limit. The `count >= cap` check in `usecase/projects.go:145` is racy — both reads see `count = cap-1`, both inserts succeed, the cap is exceeded by one. Add a `SELECT count(*) ... FOR UPDATE` or a partial UNIQUE index.

8. **Slack SSRF via legacy webhook_url.** As an org admin, POST `/v1/integrations/slack/connect` with `{"webhook_url": "http://169.254.169.254/latest/meta-data/"}` (or pick any internal endpoint). Expect 400 with "invalid webhook URL". Today it succeeds (F-14).

9. **Audit gap on Slack interactivity.** Trigger an approval decision via the Slack-signed POST (mocked or real). Verify `audit_log` has an `approval.decided` row with non-empty `actor`. Today (F-21), `actor` is empty.

10. **Workspace SSE max-age.** Open `/v1/workspaces/{id}/events`; hold the connection for 1h. Expect the server to terminate with a `event: close` frame at 5min. Today the connection lives forever (F-24).
